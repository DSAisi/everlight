# 长明设计增补 v2：可验证的工作记忆更新与自动纠错

此版替换上一版参考脚本。README.md 仍是精读与总体设计；下列裁决优先，避免继续套用旧样例。保持阶段二冻结与 production_approved=false。

| 输入 | 自动处理 | 当轮可见结果 |
|---|---|---|
| 可信宿主确认进度、最新产物或决定 | R01 入账；同库更新 R03 任务卡和独立事实；另记后台待办 | 任务卡更新完成项、未完成项和最新材料；不等梦或索引 |
| 明确更正且目标、范围及依据已核 | R05 只撤销指明的旧记录；替代记录沿用该段有效期 | 读最新有效值；无关历史继续可查 |
| 能绑定键，不能确定被纠正版本或证据不足 | 留原话和受影响时段的争议屏障；不推进相关工作卡 | 返回 disputed，不拿旧值继续自动动作 |
| 来了一条未来更新 | 按有效期存新状态，不自动解除任何旧争议 | 今天该未知仍未知；到期也要看争议是否覆盖该时刻 |
| 明确解决争议 | 显式引用争议和更新后的已接受证据；证据覆盖争议区间；提交时校验键版本 | 只解除引用的争议，其余保持 |
| 收到过期后台提案 | 同事务比较版本，拒绝过期写入 | 不盖掉用户新更正，不新建用户输入 |

工作卡由 R03 唯一负责。最新决定和文件采用受权引用，读取时在同一数据库快照解析，缓存必须同时核任务版本、决定引用版本、授权/删除版本和查询时间；文件写完、渠道接受、送达另记 R14 回执。主线实例跨频道关联必须由宿主绑定当前人、scope 和 task；不从相似文字强行认人。真实行动前复核范围、文件、收件人、约束与回执状态，不把已有第三版回执误作第二版已送达。

R01 原始入账与 R03/R05 更新以短事务为目标，模型不在 SQLite 事务内；入账时如果只能验证原话，先入原话并暂停关联动作，再补结构化提案。参考脚本中合法的旧版本用户更正带已知键和区间时，原子尝试失败后会保留原话并设置局部争议，重放不产生第二次效果。输入无法建立可信键时，应走原文入口，而不是调用已分类接口。无效结构化请求（如未知操作、伪引文）显式拒收；这不等于宿主可丢原始消息。后台只提案，使用带预期版本的写入，不冒作新的用户事件。

示例：第三版草稿已完成、禁止发送；用户明确说「还是第二版，紫色，文件已写完，下一步只查送达」→ 当轮工作卡更新 → 新窗口“继续”读出第二版和紫色 → 第三版仍禁发，且它的回执不适用于第二版 → 第二版送达未知时只请求查状态。后台晚到的旧提案因版本冲突被拒。

脚本采用 BEGIN IMMEDIATE 后再读并比较修订，写入输入、事实、工作卡、待办后一起提交；两连接同时写同一版本只允许一方成功。更正目标按记录 ID + scope + key 查找；区间使用左闭右开。参考实现限于人工标注、单值事实、明确区间和顺序追加；迟到和重叠事实可拒收或走争议，不自动重建历史。resolve 当前要求一条完整覆盖的证据；分段解争议需未来实现拆区间。自动决策已走入口，但自然语言实体/更正识别、权限服务、真实送达、Dreaming worker、RSI 评估与 DSH 宿主外壳不在脚本实现范围。未通过真实 messages、输出及故障取证前，不标为上线最终版。

运行：python3 test_replay.py（无需第三方依赖；仅临时数据）。实际结果见 replay-results.txt。
