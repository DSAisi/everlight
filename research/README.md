## 2. 时态事实：写入协议

每个可变化的事实以 canonical_key = (realm, subject_id, predicate, qualifiers) 匹配。realm 是授权范围，不是会话昵称；平台别名必须经确认映射到 person_id。qualifiers 包含项目、产物、收件人等实际限制。多值属性必须声明集合语义；新工作和旧工作可并存，不能总用新值替换旧值。

每条 ClaimRevision 保存：
- claim_id / revision / canonical_key / value / source_ref（原句片段和 source revision）。
- valid_from / valid_to（现实有效期，左闭右开）、observed_at（何时被观察）、recorded_seq（何时入库的序号）。未知用 unknown；不能拿观察时间填有效期。
- assertion_status（accepted / disputed / corrected / withdrawn），时间状态（effective / scheduled / historical / unknown）在查询时按区间得出；历史与错误不是一个枚举。
- prior_revision / transition / verification / scope / invalidation_epoch。所有修订保留来源，软失效与授权删除分开。

| 证据 | 动作 | 前台怎样读 |
|---|---|---|
| 可信来源明确说现状变了，主体和范围唯一 | 在有效边界结束旧期；创建新版本；修订同一键并登记依赖失效 | 当前用新值，历史按有效期看旧值；未来生效不提前 |
| 可信来源明确说旧事实从未成立 | 把旧主张标 corrected；派生记录立即不可作为依据 | 当前和历史事实都排除旧主张；原话仅作审计 |
| 来了一条兼容事实 | 作为新增，保留已有值与其限定 | 按谓词返回一项或一组 |
| 矛盾但对象、时期或来源可信度不清 | 保留新输入，创建 disputed 屏障，排待办 | current 对受影响键返回 unknown/disputed；局部澄清；不扩大失效到无关任务 |
| 延迟到达的历史事件 | 写入有明确期限的历史片段；重算受影响区间 | 不因最近入库成为现状 |

R01 同一事务保存输入、结构化修订（或待判屏障）、失效版本与 outbox。分类模型可以提议，但不能单独获得写权。直接自动提交限于来源可核、同范围、主体与操作唯一、证据足够且低风险的更正；不能可靠解析就先保守停用受影响视图。不能确定范围的当前请求暂停关联动作，不能全库盲清。scope/canonical_key 折叠规则由确定的领域契约维护，不能让模型靠近义词自动跨人合并。

例：10 月 2 日说“9 月就搬走了”，10 月 5 日才入库。9 月何日不清时，9 月任一指定日可能 unknown；当前可根据明确“已经搬”处理，但不能编造具体搬家日期。查询“10 月 4 日系统当时知道什么”按入库水位回放；查询“10 月 4 日现实是什么”按有效期判断，两者区别明确。

## 3. 同一轮更新工作台并安全读出

R03 的 TaskCard：task_id / scope / revision / focus / latest_decisions / deliverable_refs / completed_steps / pending_steps / constraints / action_refs / lineage。事实归 R05，实际动作与结果归 R14，文件归 R12；卡片留引用，不维护第二套真相。任务选择来自宿主显式绑定或唯一可证焦点；同名、转述、多个未结任务不得强选。

前台顺序：R21 接入 → R01 持久化 → R03/R05 最新视图 → R15 按请求选择现在、某日、历史事件或当时已知 → R16 查原句与更正链 → R22 只供应有效且需要的材料 → R14 执行前复核。

查询先过滤 scope、权限、当前删除账和相关键的修订版本，再排序。索引版本落后不能用其旧文入请求；在预算内回读规范库，仍不完整就标 partial，而不是返回空结果或旧结论。现在问法默认 current；“那天我们定了什么”绑定事件/日期。历史文本可标“曾经”，不会作为默认当前约束；必要更正整组供应。相关性排序可按当前语境自然变化，不设统一情绪/记忆触发阈值，扫描数、调用时限和预算仍有限。

输出前检查候选的键版本和治理版本；发现并发修订时重组一次，再变则撤该组并报告局限。已有请求一旦出站不能撤回模型已经看到的内容：依赖变更影响实际输出时，由宿主拦截或重算；外部动作执行前重核其精确对象及授权。未知送达不由模型猜成功，也不自动重发。R14 查询不到权威回执就保 unknown。

示例：第三版禁发，之后只准发第二版 → 禁发约束与许可分别以产物为限定 → “继续”只恢复第二版 → 旧摘要候选不能复活第三版许可 → 第二版若已有不明尝试，本轮仅查状态。

## 4. R17 做梦：把旧笔记送回复核

触发：有效期冲突、明确反馈、外部结果反转、索引落后、或空闲积压。宿主在已授权实例中触发；没有授权的外部模型调用和原文外传不开启。优先结构化核验，模型分析只处理预算内的开放问题。

1. 从已提交 outbox 取得每个范围的事件/修订序号，生成 snapshot 和确切来源版本。待处理和失败单独追踪，不能把批次读过当作所有项完成。
2. 单工作者或有租约的队列领取，受 fencing 限制；网络调用不持库锁。以 scope+source version+processor version+purpose 为幂等键。
3. Analyzer 产出 candidate patch：目标键及预期版本、原句范围、有效期、转换分类、理由与反证；以及是否影响任务、关系、情绪、方法或知识目录。不执行外部动作。
4. Organizer 合并重复、列出同源及分歧，保留独立来源。摘要、反思、模型自评不得变成新的证据根。
5. Verifier 先检查权限、来源范围、版本及支持关系；无法确定就待审。Committer 逐项比较当前版本与快照；旧快照提案必须重算或废弃，不能覆盖刚到的更正。负责模块分别提交，不假装跨库全局原子。
6. 提交后失效派生，再重建关系、工作台引用、检索索引和只读 Wiki；失败以版本水位/回执续跑。删除账优先于恢复和重跑；待生效的旧提案无权复活删除内容。

反馈闭环：用户纠正 / 工具结果 → 具体修订 → 受影响的后续请求 → 行为或回执 → 改进/无变化/未知/回归。记忆清理与策略改进分别记账。情感线只允许更新有依据的解释；短期激活回落允许发生，但沉默不转换关系状态，原话也不被后来解释覆盖。

## 5. R23 策略自改进：自动提案、对照、筛选

允许自动改变的候选项：声明式检索路线、优先查哪个库、补查顺序、注入预算分配和方法经验的适用范围。R15/R22 固定授权和证据检查不可改，R14 行动边界不可改，R23 评估集和发布批准不可改。允许反复使用经隔离评估的候选作为下一轮基线；不能据此宣称改模型本体。

失败事例分类 → 候选改动及假设 → 冻结现行/候选与输入回放 → 分别评分 → 保留谱系与失败反例 → 通过才进入隔离验证或影子观察 → 线上需独立批准。一次以一个可解释变更为主，限制预算和次数。最终留出集按任务/会话分组，防止同一个故事的改写泄漏到两边；回归用例可逐渐积累，但不得兼作独立评估。

示例策略：听到“继续”时，旧策略先用语义匹配历史；候选先用唯一 task_id 查 R03 决定与产物，再补历史。对照必须含“两个同名任务”和“最近聊天谈的是另一个项目”，不能只挑候选赢的场景。分别量化：当前事实误用率、时态问法正确率、必要召回覆盖、错范围证据、无关注入、实际输出正确率、额外耗时和开销。越权、复活删除、时态陈旧引发错误副作用是硬失败；没有足够样本就保不确定。回退仅切回策略版本，不能连带撤回用户后来更正、删除或行动回执。

## 6. 落地与验收

A. 隔离脚本先证实：明确修订无需后台、旧索引仍读不到旧现状、时态查询可回看、冲突带不确定、前台阻错误动作。
B. 接隔离宿主后，沿原冻结阶段二验收三组独立回放：关闭、开启、故障。核真实请求 messages 替换、真正输出变化、故障下仍可说话且明确局限。附真实 action_id/receipt，不能拿模拟数组或内部日志作证。
C. 开后台影子：验证延迟入账、重投、崩溃恢复、旧提案冲突、删除传播；分别报告扫描范围和实际成功。
D. 策略候选留出验证，再考虑授权接入。阶段二不借此扩范围，不重启 DSH、不装插件、不读写生产档案。

本包的 replay.py 使用临时 SQLite 和人工标注的结构化输入；验证确定性生命周期及小型任务/回执场景，不实现语义抽取、实际模型、真实宿主、后台调度或 RSI 搜索。运行 python3 replay.py，无第三方依赖。测试结果见 replay-results.txt。
